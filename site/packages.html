Reference

Packages

A manifest, a resolver, a lockfile — and a ceiling on what a dependency may do, checked at compile time in every consumer.

A manifest

[package]
name = "ecommerce_cart"
version = "1.0.0"
entry = "main.gr"
capabilities = ["io", "net"]

[dependencies.json]
path = "../../packages/json"
version = "^1.0.0"

The ceiling

capabilities is the set of effects this package may perform. Effects are inferred from source, so the claim is checked rather than trusted. A dependency that starts reading files without declaring io fails to build — and it fails in your build, not silently in theirs.

This is the part of the package system worth having. Version resolution is plumbing every language has; a supply chain where a dependency's reach is a compile-time fact is not.

Commands

grasm deps            # resolve, check ceilings, write grasm.lock
grasm deps --locked   # fail rather than update the lockfile

What ships today

654 libraries, all written inside this repository because there is no registry to get one from. The table below is a sample of them — the ones where the capability column says something worth reading.

passwordnonePBKDF2-HMAC-SHA256. The stored form carries its own algorithm and cost, so a file written today can be verified after both change.

xmlnoneParse and render. No DTD and no external entities, ever — that is what XXE is, and a first release does not need it. Which is also why this can declare nothing and mean it.
oauth2noneThe authorisation-code flow with PKCE (checked against RFC 7636's vector) and client credentials. PKCE and state are not optional here.

557 of the 654 libraries declare nothing. Only 97 ask for any capability at all. That is the pattern the whole design is for, and the number is counted from the manifests rather than asserted: reach is split from computation, so a program that joins paths, formats a date or builds a URL acquires no capability by doing so — and where a library really does need the world, it asks for it as an effect the consumer supplies, which is what log demonstrates.

They are three packages because http cannot open a socket, and that is checked rather than claimed: its manifest declares no capability, effects are inferred from its source, and a version of it that started dialling out would fail to build in every consumer. So a program can parse and route HTTP while remaining provably unable to reach the network, and a program that only builds requests never acquires the ability to send them. In every other language, depending on the HTTP library means depending on something that can.

Where packages come from

The registry is called Blade. It is not a separate program — grasm add pulls from it, grasm publish pushes to it, and grasm deps resolves against it, all from the one binary.

Two sources work today: a path dependency, and a local Blade registry under .grasm/registry (or wherever GRASM_REGISTRY points). Both resolve, lock and check ceilings.

There is no remote registry. Nothing fetches, publishes or verifies over a network yet, and there are no third-party packages to fetch. Both are on the roadmap, and they are the largest thing standing between this language and ordinary use.
