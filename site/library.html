Reference

Library reference

The standard library, clause by clause. This page is spec/library.md, rendered when the site was written — not a summary of it.

Every operation the language provides, by receiver type. There are no imports: these are always available.

Each L- clause below has a conformance program under spec/conformance/ that exercises what it claims. That is per clause, not per row: a table entry whose clause is covered elsewhere can still drift, which is how read_file came to be documented as returning Option[str] when it is fallible.

[L-LIB-CLOCK] now_millis is the wall clock and moves backwards — a correction, a leap second, a resumed machine — so a duration measured with it goes negative and a timeout fires wrong by that much. monotonic_millis only increases, and so does monotonic_nanos. sleep_millis waits; a replay does not.

[L-LIB-EXIT] exit(code) ends the program with the low eight bits of code, as an operating system reports it and as C's exit does: exit(-1) is 255, exit(256) is 0. Clamping to 0..=255 was worse where it matters — it made exit(-1), the commonest spelling of "fail" in a script, report success. exit performs no effect, so a dependency declaring capabilities = [] can end the host process: deliberate, since panic and an endless loop already do — a ceiling bounds what a dependency can reach, never how long it runs. Nothing observable outside the process changes, so charging io for it would buy no guarantee while making every program that reports a status ask for the filesystem.

[L-LIB-IO] The three ways a library call reports "no": read_file is fallible (str ! IoError) because a failure has a reason worth reading — NotFound(path), and so on. env returns Option[str], because an unset variable has no reason to give. file_exists returns bool, because the question was already yes-or-no.

Unquoted means a one-element list holding the empty string renders exactly as an empty list does: [""] and [] are both [], and "".split(",") — one field, per the table above — looks like no fields at all. That is the price of a rendering meant to be read rather than parsed, and it is stated because the alternative is a reader concluding the library is wrong. len() tells them apart.

Strings nested inside a collection are not quoted, so [a, b c] is a two-element list whose second element contains a space. Rendering is for people reading output; it is not a serialisation format and does not round-trip.

1b. Calling a free function as a method

[L-UFCS] A free function whose first parameter accepts the receiver may be called in method position: f(x, y) and x.f(y) are the same call. This applies to functions a program declares, not only to the library.

fn double(n: i64) -> i64 { n * 2 }

fn main() {
    print("{double(5)}")     // 10
    print("{5.double()}")    // 10 — the same call
}

Method syntax is resolved against the built-in methods for the receiver's type first, and a free function is considered only when no built-in matches. So declaring a function named len does not change what xs.len() means.

The language's own free functions — print, read_file, write_file, file_exists, input, args, now_millis, env, exit, panic, assert, assert_eq — are not reached this way. They are not methods of any type, and a second spelling for each of them buys nothing: x |> print already applies a free function to a value ([G-PIPE]), and it is charged the same row a call is. "hi".print() is refused, and the refusal says so and points at the pipeline.

2. i64 and f64

[L-LIB-FIXED] x.to_fixed(places) is f64 as text with exactly that many digits after the point, 0 to 17; anything else panics. Both engines format through the same code, so they agree digit for digit — which a formatter built by hand out of round and to_str cannot promise, and which is what every report with an average needs.

A value that is not finite answers with inf, -inf or NaN regardless of the requested precision, matching [L-DISPLAY].

Ties go away from zero, the same rule round uses ([L-LIB-ROUND]), so (2.5).to_fixed(0) is "3" and (0.125).to_fixed(2) is "0.13". A tie means the stored value is exactly halfway, which is rarer than it looks: 2.675 is really 2.67499…, so (2.675).to_fixed(2) is "2.67". Nothing is scaled to decide this — scaling 2.675 by 100 lands on 267.5 and would round it the wrong way.

[L-LIB-REMOVE] xs.remove(i) takes the element at i out of the list and answers with it, shifting the rest down. Out of range panics, the way indexing does — pop is the one that answers Option, because "the list was empty" is a thing a caller can reasonably not know and "index 9 of 2" is not.

This is what draining a queue from the front reads like. Without it a ready queue cost ready = ready.slice(1, ready.len()) a step, which reads like the workaround it was — but the cost is the same: remove(0) shifts the rest down, so both are O(n) per step and a full drain is quadratic either way. Measured at 80 000 elements, 17.2 s for remove(0) against 12.8 s for the slice. If a queue is what you have, reverse it once and pop from the end, which is O(1); this method is for taking an element out of the middle.

[L-LIB-SUM] xs.sum() of an empty list is the zero of the element type: 0 for [i64], 0.0 for [f64].

This held only in the compiled backend for a long time. The interpreter decides int-versus-float from the elements, and an empty list has none, so an empty float sum was 0 under grasm run and 0.0 from a native binary — and a float method on the result panicked with no method to_fixed on 0, in the engine this specification calls normative, on the empty-average case every reporting program has. It was recorded here as a known deviation on the grounds that fixing it needed the interpreter to carry element types. It did not: the checker knows the sum is an f64 and can say so, which is the same answer it now gives for a promoted literal ([T-INT-TO-FLOAT-CARRIED]).

[L-LIB-CMP] a.cmp(b) answers -1, 0 or 1 in exactly the order sort uses — [L-LIB-SORT-NAN]'s total order for floats included. It exists because that order was specified, used internally, and callable by nothing: a program needing it reimplemented it from < and >, got NaN wrong, and scrambled a column in precisely the way that clause warns about. Naming a hazard without handing over the fix is how a specification becomes a trap.

It is also what makes a comparator sort writable — several keys with directions decided at run time, which a single sort_by key expression cannot express.

[L-LIB-SORT-NAN] Floats sort by a total order: -NaN before every number, NaN after every number, and -0.0 before 0.0. This is not IEEE comparison, where a NaN is unordered with everything — < keeps that. A sort needs an order, and calling every NaN comparison "equal" is not one: given a non-order a sort returns a list that is not sorted at all, so one nan cell in a file scrambled a whole column rather than misplacing one value.

[L-LIB-ROUND] round breaks ties away from zero: 2.5 and 3.5 round to 3.0 and 4.0, -2.5 to -3.0, -0.5 to -1.0. It is not banker's rounding, and a report's figures depend on which it is. (i64_min).abs() is i64_min: there is no positive i64 that far out, and the wrap is the same one / and % take ([E-ARITH-INT]).

Every one is pure: no allocation, no error case, and no capability. That last part is the reason they are here rather than left to extern fn cos — a declared C function performs io ([T-EXTERN-VALUE]), so reaching libm for a cosine put a trigonometry helper over the ceiling of any package declaring capabilities = []. A pure function should not cost a capability.

pi and e are the only two builtins that yield to a function you declare yourself: a program with its own fn e() keeps it. e is a common enough identifier that taking it outright would break working programs.

[L-LIB-TO-STR] to_str produces exactly what print would. In particular an f64 keeps its point at every magnitude: (1.0).to_str() is "1.0". The interpreter used to hand the job to its host language, which drops the point on a whole value, so it answered "1" where the compiled backend answered "1.0" — and the documented idiom xs.map(|v| v.to_str()).join(", ") printed a [f64] as a list of integers, which [L-DISPLAY] exists to prevent.

[L-LIB-AS-I64] as_i64 is total: every f64 has an answer, so it never panics. Too large gives i64's maximum, too small its minimum, NaN gives 0 — saturation, and a clamp rather than a truncated bit pattern, because the two disagree and only one stays ordered. to_bits asks the other question, not what a float means but what it is: without it nothing can put a float in a binary format or compress a series, every such technique XORing consecutive patterns.

3. str

[L-LIB-STR] Lengths and offsets are in characters, not bytes ([E-STR-CHARS]). s.byte_len() is the one exception and is the only way to ask the other question: "🙂".len() is 1 and "🙂".byte_len() is 4. Characters are the right unit for a high-level language and the wrong one the moment a program writes a string to a socket or a file and has to say how long it is — a Content-Length counts bytes, and computing it from len() is wrong for every string that is not ASCII.

[L-LIB-TRIM-SIDES] trim_start and trim_end remove whitespace from one end only; trim removes it from both. None of the three takes an argument — whitespace is what they trim. The one-sided pair exists because a line's leading indentation usually carries meaning and its trailing newline does not, and trim cannot tell you that.

[L-LIB-CODES] s.code_at(i) and s.codes() give Unicode code points (char scalar values), counting characters not bytes, and n.to_char() turns one back into text. code_at panics out of range, like indexing; to_char panics on a value that is not a code point, surrogates included. Together they are what lets a program compute on text — hash it, encode it, parse a number by hand — rather than only cut and compare it.

len, code_at and substr all answer in constant time (substr in time proportional to the slice it returns), whatever the text. They count characters, so each used to decode the string from the start: while i < s.len() was quadratic in two ways at once, and 400 000 characters took 6.7 seconds where the identical loop over a list took 0.21. A string never changes once built, so its character count is computed once and kept. When that count equals the byte count the text is ASCII and an index is an index; when it does not, a character index is built once, the first time one is asked for by position. Fixing only the ASCII half left the same 6.3 seconds waiting behind a single two-byte character, and building the index for code_at while leaving substr to walk from the start left a substr(i, 1) scan quadratic — 39 seconds over 262 144 characters — next to a code_at scan of the same string costing 0.11.

[L-LIB-WORDS] s.words() splits on runs of whitespace and yields no empty elements, which is what reading a line of aligned columns needs. s.split(" ") is the other thing — an exact separator, where two spaces in a row mean an empty element between them — and both are worth having, because a CSV wants the second and a log line wants the first.

[L-LIB-PARSE] parse_int and parse_float answer None for text that is not a number, and are worth stating exactly because untrusted input reaches them:

  • parse_int accepts surrounding whitespace and a leading + or -. It does not accept the 1_000 and 0xFF forms that [L-INT] allows in source: a literal in a program and a number in a data file are different things.
  • parse_float accepts inf, -inf and nan, and a value too large to represent gives an infinity rather than None. So "1e400" parses, and the inf it produces then flows into arithmetic, as_i64 ([L-LIB-NUM]) and sorting ([L-LIB-SORT-NAN]) — which is how those three came to be specified.

[L-LIB-SORT-BY] xs.sort_by(key) sorts by what key returns for each element, which is where a list of structs gets its order from — sort needs the elements ordered, and a struct is not. The key is i64, f64, str, or a tuple of those, which is what makes xs.sort_by(|p| (p.dept, p.age, p.name)) a multi-key sort rather than an error ([L-LIB-TUPLE]). This clause said "must be i64, f64 or str" while tuple keys worked in all three engines — two clauses of one document disagreeing, and the one that was wrong was the one a reader would find first. The sort is stable: elements with equal keys stay in the order they were written. It sorts ascending, always; descending is xs.sort_by(k) followed by xs = xs.rev(). Negating the key works for a number and has no counterpart for a str, so the reversal is the general answer and the one to reach for. The assignment is the whole point: sort_by mutates and rev answers with a new list, so the clause's earlier wording — xs.rev() on its own line — left the list ascending and said nothing.

[L-LIB-PAIRS] xs.enumerate() pairs each element with its index and xs.zip(ys) pairs the two lists positionally, stopping at the shorter — there is no element to invent past the end of one. Both give [(A, B)], which for (a, b) in … binds by name ([G-LET-TUPLE]).

[L-LIB-TUPLE] A tuple's components are read by position — pair.0, pair.1 — and a tuple of ordered components is itself ordered, compared component by component. That is what < on tuples means, what sort on a list of them does, min/max included, and what makes xs.sort_by(|p| (p.dept, p.age, p.name)) a multi-key sort rather than an error. min and max used to spell out the types they accepted instead of asking whether the element was ordered, so xs.enumerate().min() was refused on a list sort orders happily.

That example is worth spelling out, because it does not mean "index of the smallest": components compare left to right, so enumerate().min() compares indices first and always answers (0, xs[0]). To find the smallest and where it was, put the value first — xs.enumerate().map(|p| (p.1, p.0)).min().

[L-LIB-RANGE-OPS] A range answers to_list, map, filter, sum and len, producing a list of the same elements for i in a..b walks. There is one definition of what a range contains and not two: every engine builds that list and reuses the list method.

A range is also a value: let r = 0..n binds one, it prints as 0..n rather than as its elements, and two compare equal when their bounds and their inclusiveness match — so 0..3 == 0..3 and 0..3 != 0..=3. It holds three numbers and not its elements, so 0..2_000_000 costs the same as 0..2.

Its type is written range: fn window(n: i64) -> range, type W = { span: range }, [range]. That name reached the error messages before the syntax, so a range could be bound and never declared — a value you can hold and cannot pass is stuck in one function body. It reaches its methods from any shape that produces one, not only from a name: [0..3][0].len() and window(2).sum().

len is answered from the bounds without building anything; the others build the list first. for i in a..b written literally never builds a range at all — it is compiled into a counted loop — and that is why the loop costs nothing and holding a range costs one allocation.

The clause exists because of what it replaces. Building a list from a count needed var xs: [i64] = [], a for, a push and two closing braces — four lines where (0..n).map(f) says the same thing, in every program that builds a list from a count. [G11] budgets Grasm at or below Python's token count and it measured 1.41×; this is most of the difference, and adding it moved the figure to 1.22× without adding a syntactic form — a call is a call, so the kernel's count in core.md does not move.

Network — the net capability

tcp_connect resolves names; failing to resolve and failing to connect are the same IoFailed, since both mean "there is nothing to talk to", and the message carries the difference. A handle is an integer and a payload is text, so the network needed no pointer type and no byte buffer in the language.

tcp_read performs one read rather than looping to end-of-stream, because an HTTP client holds the connection open after its request and reading to the end would wait forever. A caller that needs more reads again. Bytes that are not valid UTF-8 are replaced rather than refused: a socket carries bytes, a str carries text, and a client's mistake should not end a server.

That is wrong for a protocol not made of text: a JPEG in multipart/form-data would arrive plausibly sized and broken. tcp_read_bytes and tcp_write_bytes are the same calls without the conversion ([L-LIB-BYTES]). Both pairs stay: an HTTP header is text and its body may not be.

net_port is what makes tcp_listen(0) usable. Letting the system choose a free port is how a program runs where the one it wanted is taken, and without reading the choice back it could not name, dial, or print the port it bound.

net_wait is what lets one thread hold many conversations. Every other call here blocks, and spawn does not carry net, so without it a server serves one client at a time; several such loops at once are [L-LIB-NET-WORKERS].

It answers with the subset of hs that will not block, in the order they were asked in rather than whichever order the kernel reports, so a program that walks the result serves its connections in a fixed order ([L-DETERMINISM]). A timeout of 0 asks without waiting, a negative timeout waits indefinitely, and an empty wait set is answered immediately with an empty list rather than an error — a server that has just closed its last connection asks exactly that on its next turn. A handle that names nothing is an IoFailed, the same as using a connection after closing it.

A hung-up peer is reported as ready. The read that follows returns nothing, which is how a caller learns the conversation ended; reporting it as not-ready would leave a dead connection in the wait set forever, and the loop would never notice it should be dropped.

[L-LIB-NET-PEER] tcp_peer(h) is the far end of an accepted or dialed stream; any other handle is an IoFailed. Those streams have Nagle off (TCP_NODELAY).

[L-LIB-NET-WORKERS] net_workers(n, f) runs f(0), …, f(n - 1), which may run concurrently, and answers their results in index order. A compiled build gives each a thread, joined before the call returns; grasm run, and any recorded or replayed run, calls them one after another in index order. f may perform net and nothing else, and may not reach a ref or an actor handle from outside ([T-PAR-MAP-PURE]): workers share the socket table and nothing more, so the only concurrency is the network's, which no program controls anyway. n <= 0 answers []; n > 256 panics, as does a panicking worker. A tcp_accept on a listener this thread's last net_wait reported ready does not wait: if another worker took the connection, it is an IoFailed.

[L-LIB-UDP] Four more reach the network as datagrams, each performing net:

type
udp_bind(port)(i64) -> i64 ! IoErrorbinds a datagram socket; 0 asks the system to choose
udp_send(h, host, port, b)(i64, str, i64, bytes) -> i64 ! IoErrorsends one datagram, answering with the bytes sent
udp_recv(h)(i64) -> bytes ! IoErrorreceives one datagram, whole
udp_recv_from(h)(i64) -> (bytes, str, i64) ! IoErrorthe same, and where it came from

UDP is not TCP with the reliability removed but a different shape. A stream fixes both ends at connect time; a datagram is a whole message with no fixed peer, so udp_send names a destination every call and udp_recv_from answers the sender's — a receiver that cannot learn who wrote can only answer peers configured in advance ([L-LIB-PROC] for why a tuple).

Payloads are bytes, not str: the protocols that use UDP are binary, and routing a DNS query's bit-level flags through the lossy UTF-8 conversion the stream operations correctly use for text would corrupt it ([L-LIB-BYTES]).

A read returning half a message, or two joined, would destroy the only thing UDP guarantees. Nothing past 65535 bytes arrives over IPv4 in one piece, so the buffer cannot truncate a deliverable datagram.

Datagram handles share the table with stream handles, so net_wait, net_port and net_close work on all three kinds unchanged. A program that speaks two protocols multiplexes them in one loop, which is the ordinary case rather than an advanced one. Using a stream operation on a datagram handle is an IoFailed naming the operation to use instead.

Closing a handle twice is not an error, for the same reason releasing a ref twice is not ([T-REF-GENERATIONAL]) — cleanup order is not something a caller should have to track. Using a closed handle is an error, and an ordinary one: tcp_read on it answers Err, never a panic and never a wrong answer.

net is a capability of its own, not part of io. That distinction is the whole point. [T-CAPABILITY]'s headline example is a package permitted to read a file and forbidden to open a socket, and until there was a network to gate, that example could not be shown to anybody:

error: package `lib` performs `net` but its manifest only permits `io`
  help: either add the capability to that package's manifest, or stop it from
        performing the effect

[L-LIB-BASE] n.to_base(b) writes an integer in base b and s.parse_int_base(b) reads one back. Digits are 0-9a-z, lower case, and a negative number gets a leading -.

Base ten is not the only base a systems program needs. Every protocol, hash, colour and permission mask is read and written in hex or binary — the same programs that needed [L-LIB-BITS] — and without these, printing a packet ID the way every other tool prints it means hand-writing a digit table.

A base outside 2..36 panics rather than answering. There is no right answer to return and a wrong one would be silently wrong, which is the same reasoning as code_at panicking out of range.

Neither side writes or accepts a prefix. The base is the argument, not something to be guessed from the text: "ff".parse_int_base(16) is Some(255) and "0xff".parse_int_base(16) is None. That keeps it consistent with parse_int, which refuses 0xFF ([L-LIB-PARSE]) — the difference is now that a program can say which base it means instead of being stuck with one.

to_base(10) and to_str agree, including at i64::MIN, which is converted through its unsigned magnitude because negating it overflows.

Processes — [L-LIB-PROC]

[L-LIB-PROC] proc_run(program, args) runs another program to completion and answers with (exit code, stdout, stderr):

type
proc_run(prog, args)(str, [str]) -> (i64, str, str) ! IoErrorperforms proc
proc_pipeline(stages, input)([(str, [str])], str) -> (i64, str, str) ! IoErroreach stage's output feeds the next

proc is a capability of its own, and it is strictly larger than io or net. A program that can run curl has the network whether or not it declared net; one that can run rm has the filesystem. Folding process execution into io would make every capability claim in the language weaker than it reads — a package's manifest could say io and mean everything.

The result is a tuple, not a new type. Three values with obvious positions did not need a name, and inventing one would have put a type in the prelude that nothing else uses.

Output is captured, not inherited. A builtin that wrote to the parent's stdout would make the three engines disagree about ordering, because the child's writes and the parent's go through different buffers. A caller that wants the output shown prints it, which also means it can be examined first.

args are passed as a list and never through a shell, so a filename containing a space or a ; is one argument and not an injection. A program that genuinely wants shell semantics asks for them: proc_run("sh", ["-c", line]).

proc_pipeline exists because a pipeline cannot be built out of proc_run. That waits for a program to finish and hands back its output, and a pipeline needs one child's stdout to be another's stdin. Copying the bytes through Grasm instead would need concurrent reads and writes on pipe handles — a much larger surface for a smaller result, and the kernel already does this.

input feeds the first stage's stdin, which is the other thing proc_run could not do: a filter with nothing to filter is not a filter. It is written on a thread, because a large input and a chatty child deadlock if the parent writes everything before it reads anything. An empty input closes stdin rather than leaving it open, so a stage reading to end-of-input does not wait for input that is never coming.

The result is the last stage's exit code, stdout and stderr, which is what every shell means by a pipeline's status. An earlier stage's stderr goes to the program's own stderr rather than being discarded: a diagnostic nobody sees is worse than one in the wrong place. If any stage cannot be started, everything already running is killed and the whole call is an IoFailed — a pipeline that failed halfway leaves nothing behind. An empty pipeline is an error, not a silent success.

An exit code of -1 means a signal killed the process. No process can exit with -1, so it cannot be confused for a status the program chose. A program that could not be started at all is an IoFailed naming it, which is a different thing from a program that ran and failed.

Bit manipulation — [L-LIB-BITS]

[L-LIB-BITS] Seven methods on i64:

a.bit_and(b)(i64, i64) -> i64bitwise and
a.bit_or(b)(i64, i64) -> i64bitwise or
a.bit_xor(b)(i64, i64) -> i64bitwise exclusive or
a.bit_not()(i64) -> i64ones' complement
a.shl(n)(i64, i64) -> i64shift left
a.shr(n)(i64, i64) -> i64shift right, sign-preserving
a.ushr(n)(i64, i64) -> i64shift right, zero-filling

Methods rather than operators, and the reason is that every symbol is already taken or ambiguous. ^ is exponentiation. | begins a closure and separates sum-type variants, so a | b cannot be told from the start of one. && is already reported as "written and". And words would collide with the logical operators, which in this language are and, or and not — so a and b would be boolean and a band b bitwise, one letter apart. Methods are what .abs() and .cmp() already are, and they carry their own precedence.

The shift count is masked to 0..63. 1.shl(64) is 1, not 0 and not a trap, and 256.shr(-1) is 256.shr(63), which is 0. This is what the hardware does, and it is stated because the alternatives are worse: Rust's << panics in a debug build and wraps in a release one, which is the class of difference-between-builds this project refuses to ship, and Cranelift leaves an out-of-range count undefined, which would make the two engines disagree.

shr preserves the sign and ushr does not, which is the only reason both exist: (-16).shr(2) is -4 and (-16).ushr(60) is 15.

There is no unsigned integer type, so a program working in 32 bits masks with 0xFFFFFFFF itself. spec/conformance/L-LIB-BITS.gr shows the rotation that SHA-256 needs, written that way.

The other stream — [L-LIB-EPRINT]

[L-LIB-EPRINT] eprint(v) writes to standard error. It is print in every other respect: same single argument, same interpolation, same refusal to take a fallible value, same io effect.

It exists because a program that cannot separate its diagnostics from its output cannot be used in a pipeline, and being usable in a pipeline is most of what a command-line tool is for. A benchmark's timings, a compiler's warnings and a tool's progress are all diagnostics; sending them to stdout puts them in the middle of the data, which is the one place they cannot be noticed and the one place they do damage. It is the same reason a panic does not go there ([E-PANIC-EXIT]).

Both engines write the two streams independently and identically. The compiled build brackets the write with a flag the runtime reads, rather than carrying a second copy of the formatting code — one code path, so the two streams cannot format differently.

Files and directories — [L-LIB-FS]

[L-LIB-FS] Two additions to the file surface:

type
make_dir(path)(str) -> () ! IoErrorcreates the whole path; already existing is success
remove_file(path)(str) -> () ! IoErrordeletes; a missing path is NotFound
list_dir(path)(str) -> [str] ! IoErrorentry names, sorted

make_dir creates every missing component and treats an existing directory as success, so a program can prepare its own working directory without first asking whether one is there.

Without these a file could be created and truncated but never removed, a directory could not be read at all, and a program could not make one — so a program that made a temporary file could only empty it, and the next run saw a leftover.

list_dir sorts. A filesystem's own order differs between machines and between runs, and principle 6 makes determinism a feature: an unsorted listing would make any program that printed one untestable, and would break three-engine agreement on the first run. Both engines sort, and identically.

Names are returned, not paths — the caller already knows the directory it asked about, and joining is one concatenation.

Bytes — [L-LIB-BYTES]

[L-LIB-RANDOM] random_bytes(n) answers n bytes from the operating system's entropy source, and performs io.

It is charged io because it reaches outside the program and two calls do not agree — the same reason the clock is. A pure function that answered differently each time would break every promise an effect row makes.

The primitive is bytes rather than an integer or a float because everything else is built from it and the conversions are where the mistakes are: a number in a range wants rejection sampling, not a modulo, and a language that shipped random_int(lo, hi) with a modulo in it would have shipped a bias.

n of zero is an empty answer rather than an error. A negative count, or one past 1048576, is refused — a count is usually something a program computed, and a mistake there should be a refusal rather than a gigabyte.

A short read is a failure, not a short answer: a caller asking for 32 bytes of key material and receiving 12 must not proceed.

[L-BUNDLE-SOURCE] A whole program may be written as one source file: a source bundle, in which each module is preceded by a line reading //!module <name> and the entry module comes first. Nothing is renamed and nothing is rewritten, so a bundle loads exactly the modules the filesystem would have, and a single-module program is a bundle of one.

grasm build <file> --source -o <out>.gr writes one. Every command that opens a program opens a bundle, because the detection is in the loader they share.

This exists for embedders that have no filesystem. The wasm engine takes one source string, and an import cannot be resolved by reading a file that is not there — so without this, a program with a single import could not run in a browser however small it was, and almost every real program has one.

[L-LIB-BYTES] bytes is a contiguous run of bytes, and it is the type str deliberately is not.

A str is text: UTF-8, with anything above 127 re-encoded on the way out — correct for text, fatal otherwise. Asked for the seven bytes of mov rax, 1 a str put nine on disk, and a language whose only sequence type does that cannot emit an object file.

type
bytes_of(list)([i64]) -> bytesevery element must be in 0..255
s.to_bytes()(str) -> bytesthe UTF-8 encoding of the text
b.to_str()(bytes) -> strlossy, as tcp_read is
b.len()(bytes) -> i64count of bytes
b.is_empty()(bytes) -> bool
b.at(i)(bytes, i64) -> i64one byte, 0..255; out of range panics
b.slice(from, end)(bytes, i64, i64) -> bytesend exclusive, as list.slice; out of range panics rather than clamping
b.index_of(byte, from)(bytes, i64, i64) -> Option[i64]first position >= from holding byte; None when absent or byte is outside 0..255; from outside 0..=len panics
b.concat(other)(bytes, bytes) -> bytes
b.to_list()(bytes) -> [i64]
read_bytes(path)(str) -> bytes ! IoErrorthe whole file
write_bytes(path, b)(str, bytes) -> () ! IoErrorreplaces it
read_bytes_at(path, off, n)(str, i64, i64) -> bytes ! IoErrora range; short at the end, empty past it
append_bytes(path, b)(str, bytes) -> () ! IoErroradds to the end, creating the file
file_size(path)(str) -> i64 ! IoErrorwithout reading it
sync_file(path)(str) -> () ! IoErroron the disk before answering
rename_file(a, b)(str, str) -> () ! IoErroratomic where the platform allows

The last five exist because whole-file calls cannot express data: a table larger than memory is unreadable, a log rewritten per record is quadratic, and a crash-safe commit is write-beside, sync_file, rename_file.

bytes is distinct from [i64] on purpose. A list of integers cannot promise its elements are bytes, stores eight per element, and cannot be handed to a buffer — the promise is the type. at gives 0..255; one integer type is the trade. It prints as hex, and to_str is lossy for tcp_read's reason.
