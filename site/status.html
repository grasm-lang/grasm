Status

Every number here comes from the repository as the site is written, or out of the document that recorded the measurement. Five figures here used to be typed by hand instead. Four of them were wrong by the time anybody looked — the worst by a factor of two — and the fifth, “0 open defects”, was a claim no gate on this page makes. The scorecard has all 11 goals and where each one stands.

Interpreter, bundle and native builds agree byte for byte on stdout, exit code and diagnostics. 224 are also compiled for x86_64 and run under Rosetta, 195 of them agreeing and the rest declined. Every generated program is checked for what it keeps as well as for what it prints.

Which run wrote which figure

The corpus is 511 standalone programs, counted as this page is written and by difftest's own filter — so a program added today is in that number today. Everything below it needs a run, and these are not all from one run. site/facts.json used to carry no date at all, which is how a September figure sat on this page under a sentence claiming every number came from the run that proved it; it carries one per figure now, and this is the whole record:

Two of these want reading carefully. The crosstest figure above is a clean run over the corpus as it stood in September: every program cross-compiled and every one agreed, which is what that gate demands — it fails on a program it could not build. The figure the scorecard cites instead is from October, attempted 224 programs, and was taken on a machine at load 38 rising to 134; docs/binary-size.md says in as many words that it should be taken again on a quiet machine before anybody calls it green. So the current figure is the worse one and the clean figure is the older one, and neither is the sentence anybody wants. The other is difftest, which also has two records: the row above is what the September run wrote into site/facts.json, and the October one cited earlier covers all 511 programs. This table is that file and nothing else, so the older record is the one in it.

The depth figure is a capacity, not a limit, and it is only comparable with itself. A frame holds the locals of whatever function is recursing, so the number moves with the shape of the program measuring it: the gate's own function reaches 31444, where the one in ProjectGold/08-fibonacci reached about 42,000 on the same build. That is why the gate pins one shape and asks not to have it tidied. What the specification promises is 10,000, and what the gate fails on is the margin falling under twice that — the smallest margin in which a frame doubling is caught here rather than by the guarantee breaking. It is in the table because the margin moved once already with nothing noticing: see F99.

What is not claimed

Grasm is not faster than Rust, Go or Zig, and no benchmark here says it is. It is not battle-tested. Defects are still being found at roughly one per working session — falling, but not zero, and a language with zero known defects and no users has told you more about its test suite than about itself.

The no_std conversion that took a hello-world from 351.1 KB to 85.7 KB found nine defects on its way, and no gate on this page would have caught any of them: they were in the operating-system layer, below everything the corpus exercises. Two would have shipped silently — a variadic open passing a garbage mode, and an RwLock releasing the wrong lock. The list is on the scorecard.

How that is kept honest

All 100 findings are written down in ProjectGold/FINDINGS.md, including the ones that were the test harness's fault, the ones withdrawn as wrong, and the ones caught before they shipped. Every gate is verified by breaking the thing it guards and confirming it fails — and one of them had to be, because replaytest was matching 0 of 39 journalled builtins and exiting 0 for weeks, its pattern expecting a struct written on one line. It now asserts its own count, which is the check that would have caught it on day one.
